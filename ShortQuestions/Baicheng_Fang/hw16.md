## 1.What are the three pillars of observability, and what is the primary purpose of each? ##
1. Metrics: What is happening?
Aggregated stats that tell us what is happening but it does not know any details.
2. Logs: What happened?
Structured or unstructured records of discrete event. Too much data to aggregate.
3. Traces: How did it happen?
Samples of data for debugging. With timestamps for causal profiling. But only small pieces of data.

## 2.Explain the four common metric types and give an example use case for each. ##
1. Counter - Monotonically Increasing Value
Track cumulative events over time like:  
- Total HTTP requests
- Total errors
- Total logins
can be used to calculate:
- Request rate (RPS)
- Error rate
- Throughput
2. Gauge - Current Value Snapshot
Track value that fluctuate.
- Current CPU usage
- Memory usage
- Active DB connections
- Queue Size
- Number of active users
3. Histogram - Distribution of Values
Measures the distribution of values across predefined buckets. Used for understanding latency, response times, payload size.
- API request latency
- DB query duration
- File upload size
4. Summary
Also measures distributions but calculates percentiles directly (p95, p99)  
Unlike histograms, summaries calculate quantiles on the client side.

## 3.What is structured logging, and why is it preferred over unstructured (plain text) logging in production systems? ##
Structured: writing logs in a consistent, machine-readable format (usually JSON or KV pair).  
- It is better because logs are not only read by humans - they are processed by log platforms like Prometheus. 
- With structured logs we can query: level = ERROR, userId = 007, statusCode >= 400
- Enable reliable filtering and indexing
- Better for distributed systems since they can include traceId, spanId, serviceName of the microservices.
- Easier Aggregation & Metric Extraction (Aggregate errors by region, build dashboards from specific fields)
- Automation & Security Monitoring

## 4.Explain the relationship between Trace, Span, and Context Propagation in distributed tracing. ##
They work together to let us follow a single request across multiple services in a distributed system.  
1. Trace: The Entire Request Journey
A trace represents the complete lifecycle of a single request as it flows through multiple services.
```txt
Client → API Gateway → Auth Service → Payment Service → Database
```
- Identified by a Trace ID
- All related spans share the same Trace ID
2. Span: A Single Unit of Work
A span represents one operation within a trace.
- HTTP request handling
- DB query
- External API call
- Cache lookup
Each span contains:
- Span ID
- Trace ID
- Start time
- End time
- Duration
- Metadata (tags, errors, status)
- Optional parent span
```txt
Trace ID: qwer1234

Span 1: API Gateway (root span)
    Span 2: Auth Service
    Span 3: Payment Service
        Span 4: Database Query
```
Spans from a tree structure with One root span and multiple child spans. 
Show what happened inside the trace, step by step.
3. Context Propagation: Passing the Trace Across Services
Context propagation ensures all services involved in a request use the same Trace ID.

## 5.Prometheus uses a "pull" model for collecting metrics. Explain how this works and what are its advantages and disadvantages compared to a "push" model. ##
Prometheus actively scrapes (requests) metrics from applications at regular intervals. Instead of applications sending metrics somewhere, Prometheus:
- Maintains a list of targets (services, pods, VMs)
- Sends HTTP requests to each target's /metrics endpoint
- Collects metrics in text format
- Stores them as time-series data

Pros:
1. Simpler, application only expose /metrics
2. Better Service Discovery
Integrates with
- EC2
- Kubernetes API
Automatically discovers:
- New pods
- Scaled replicas
- Restarted services
3. Built-in health monitoring
- If Prometheus cannot scrape a target, it knows immediately and mark the target as down.
4. Centralized Control
5. Easier Debugging

Cons:
1. Not Ideal for Short-Lived Jobs
If a job finished before next scrape, Prometheus misses it. (Batch job)
2. Scaling Difficulty
Large system with thousands of targets, high scrape load.
3. Harder to pull in restricted networks

## 6.What are the four main components of the Kubernetes control plane, and what is the responsibility of each? ##
1. kube-apiserver
The API Server is the central entry point for all cluster operations.
```txt
kubectl apply -f deployment.yaml 
```
2. etcd: single source of truth
A distributed, consistent KV store.  
It stores the entire cluster state:
- Pods
- Deployments
- Services
- COnfigMaps
- Nodes
- Secrets
If etcd is lost, the cluster state is lost.
3. kube-scheduler
The scheduler assigns newly created Pods to Nodes (but not start them).  
- Watches for unscheduled Pods
- Evaluates available nodes
- Applies scheduling policies (CPU/Memory requirements)
- Binds Pod to a Node
4. kube-controller-manager
multiple controllers that maintain desired state.  
- Deployment controller: Ensures correct number of replicas
- Node controller: Detects failed nodes
- ReplicaSet controller: Maintains Pod count
- Job controller: Ensures batch jobs complete
- Endpoint controller: Updates service endpoints

## 7.What is kubelet and what role does it play on a Kubernetes worker node? ##
Kubelet is the primary agent that runs on every Kubernetes worker node.  
Kubelet ensures that containers described in PodSpecs are running and healthy on its node.
1. Watches the API Server
kubelet constantly watches the API server for Pods assigned to its node.
```txt
Pod scheduled to Node-1
```
2. Creates & Manages Containers
- Pulls container images
- Talks to the container runtime
- Starts containers
- Mounts volumes
- Applies resource limits
It uses Container Runtime Interface (CRI) to communicate.

3. Performs Health Checks
- Monitor Node health
- Restart node automatically if it fails

## 8.What is etcd in Kubernetes, and why is it critical to the cluster's operation? ##
ectd is the single source of truth for the entire Kubernetes cluster.  
```txt
kubectl apply -f deployment.yaml
```
1. The API Server
- Validates the request
- Writes the desired state to etcd
2. Controllers:
- Watch etcd (via API Server)
- Act to match actual state to desired state
3. Scheduler:
- Reads cluster state from ectd
- Assign Pods to corresponding Nodes

## 9.What is kube-proxy and how does it enable Service networking in Kubernetes? ##
kube-proxy is a network component that runs on every Kubernetes worker node.
It enables Service networking by maintaining iptables or IPVS rules. It watches for Service end Endpoint changes from the API server and routes traffic from a Service's virtual IP to the appropriate backend Pods, providing load balancing and stable network access.

## 10. How does the Kubernetes Scheduler decide which node to place a Pod on? What factors does it consider? ##
Step1: Filtering (Eliminate Unqualified Nodes)
1. Resource Requirements
- CPU
- Memory
- Ephemeral storage
- Extended resources (GPU)

2. Node Selectors
```yaml
nodeSelector:
  disktype: ssd
```
Then only nodes with that label qualify.

3. Node Affinity Rules
4. Taints and Tolerations
5. Node conditions
- Ready
- Not under disk/memory pressure
- Not cordoned

Step2: Scoring (Pick the Best Node)
1. Resource Utilization
- Spread workloads evenly?
- Or pack tightly to free other nodes?

2. Pod Affinity / Anti-Affinity
- High availability
- Reducing single point of failure

3. Topology Spread Constraints
- Nodes are distributed across zones, Nodes, Racks
4. Image Locality
- Prefer nodes that already have the container image cached.
5. Inter-Pod Affinity
- Place Pods near related services to reduce network latency.

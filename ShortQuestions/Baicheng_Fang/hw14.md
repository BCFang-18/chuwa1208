## 1. In the CAP theorem, why is Partition Tolerance (P) considered mandatory in a real distributed system? Given that P is mandatory, what is the actual trade-off a system designer must make? ##
In a real distributed system, you cannot guarantee reliable communication. Because network is unreliable in its nature. TCP can guarantee reliable to some extends, but it is a one-to-one connection only tho.  
In a multiple servers and clients system, packets would get delayed or lost, nodes can be temporarily isolated.
If a system is not partition-tolerant, the moment this happens the system is block forever or crash.  

When no partition occur, we can have all CAP but when partition happens, we have to choose between:  
Consistency(C) and Availability(A).  

For systems where correctness matters the most, choose C.  
- Some nodes stop accepting writes
- Reads may be rejected
- System is not fully available

Examples: ZooKeeper, HBase, Spanner

For systems where uptime matters more than immediate correctness, choose A.  
- Always respond
- May return stale or conflicting data
- Both sides accept r/w
- Reconcile data later
- Eventual consistency

Examples: Cassandra, DynamoDB

## 2.Explain the difference between linearizability and eventual consistency. Give one real-world system example for each. ##
### Linearizability ###
The strongest consistency model in a distributed system.  
- Every operation appears to happen atomically
- All clients observe one single, global order of operations
- A read always returns the most recent successful write  
- Real-time ordering is preserved
- Feels like a single machine

Cost  
- Higher latency
- Reduced availability under failures
- Coordination (quorums, leaders, consensus)

### Eventual Consistency ###
Weak consistency  
- Writes propagate asynchronously
- Different replicas may temporarily disagree
- If no new writes occur, all replicas will eventually converge
- Not real-time
- Staleness is temporarily allowed
- Reconcile any conflicts later

Benefit  
- High availability
- Low latency
- Scalability

Real-world example  
Linearizability: Google Spanner  
- TrueTime: atomic clocks + GPS
- Paxos-based replication  
Why linearizability: Financial transactions, global invariants


Eventual consistency: DynamoDB  
- Replicas accept writes independently
- Data propagates asynchronously
- Conflicts resolved via vector clocks, last-write-wins
Why weak consistency: scalability, low latency, user activity feeds


## 3.What is a vector clock? How does it determine whether two events are causally related or concurrent? Why can't we simply use physical timestamps instead? ##
A logical clock that represents causality by a vector of timestamps on all nodes.  
Events happened on Node(i): ++T[i]
Node(i) sends message: ++T[i] then include in m  
Upon receiving message: T[i] = max(T[i], T'[i])++
- V(a) < V(b) iff a -> b
- V(a) = V(b) iff a = b
- V(a) || V(b) iff a || b

Physical clock may not represent causality correctly.  
For example A sends m1 to B and C at t1. B receives m1 and send m2 to A and C at t2.  
Due to network delay C may receive m2 then m1, from physical clock m2 > m1 but in causality m1 > m2.

## 5.Describe the quorum condition (W + R > N) in leaderless (Dynamo-style) replication. What happens if this condition is not satisfied? ##
- N: total number of replicas for a key
- W: number of replicas that must acknowledge a write
- R: number of replicas that must respond to a read

W + R > N guarantess that every read overlaps with the latest write.

If a write is stored on W replicas and A read queries R replicas. When W + R > N then at least one replica must be common between the write set and the read set.  
That overlapping replica:
- Has the latest version
- Ensures the read can see it

If condition fails, read may be stale.

## 6.Compare Two-Phase Commit (2PC) and the Saga pattern for distributed transactions. What is the main weakness of 2PC that Saga avoids, and what guarantee does Saga sacrifice in return? ##
### 2PC (ACID) ###
1.Prepare Phase
- Coordinator asks all participants: "Can you commit?"
- Participants lock resources and reply Y/N
2.Commit Phase
- If all reply Y -> coordinator sends COMMIT
- Else -> ABORT

Guarantees
- Atomicity
- Strong Consistency across participants
- ACID semantics

### Saga Pattern (Best effort) ###
A sequence of local transactions, each with a compensating actions.
- No global lock
- No central blocking coordinator
- Transactions commit independently
- Failures are handles by rollbacks

In 2PC, if the coordinator crashes after participants vote YES but before COMMIT:
- Participants must block
- They hold locks
- They cannot decide commit or abort on their own
- Stop the world

Saga however completely avoids this:
- No global lock
- No waiting for a coordinator to recover, commit independently

At the cost of global ACID consistency. 
Some side effects cant be erased

Pros:
- Availability
- Scalability
- Fault-tolerant

Orchestrated Saga actually has a coordinator but no global locks, no "prepare" phase, participants commit immediately.

## 8.What is a CRDT (Conflict-free Replicated Data Type)? Explain how a G-Counter works and why it always converges without coordination ##
CRDT is a data structure designed so that multiple replicas can be updated independently and concurrently, and will always converge to the same state without coordination. 
- updates are local
- replicas do not need locks, leaders, or consensus
- conflicts are resolved mathematically, not procedurally
- replicas converge using merge operations

G-Counter is a counter that
- Only increase
- Replicated across nodes
- Supports local increments
- Converges by merging with max

Each replica keeps a vector of counters, one entry per replica:  
```text
Replica A: [a, b, c]
```
- a: number of incs performed by A
- b: number of incs A knows B has done
- c: number of incs A knows C has done
The value of the counter is the sum of all entries.  
1. Increment(local, no coordination)
2. Merge (element-wise max)

Why a G-Counter always converges?
1. Commutative
2. Associative
3. Idempotent

Pros:
- No locks
- No leader
- No quorum
- No rollback
- No conflict resolution logic

Cons:
- Weak consistency (eventual consistency)
- No real-time ordering
- No decrement


## 9.Explain the Circuit Breaker pattern. What are its three states, and how does it prevent cascading failures in a microservices architecture? ##
Circuit Breaker pattern is a resilience pattern used in microservices to stop repeated calls to a failing service and give it time to recover-preventing failures from spreading through the system.  
Three states: CLOSED (failures) -> OPEN (cooldown) -> HALF-OPEN (success) -> CLOSED

Without Circuit Breaker:
- Service A calls Service B
- B fails
- A keeps trying, threads block waiting
- A runs out of resources
- Services depending on A now fail as well


## 10.What is the difference between range-based partitioning and hash-based partitioning? What problem does consistent hashing solve compared to simple hash-mod-N partitioning? ##
### Ranged-based partitioning ###
- Keys are divided into ordered ranges
- Each shard owns a contiguous interval

Pros:
- Supports range queries efficiently
- Natual ordering
- Good for time-series data

Cons:
- Hotspots (popular ranges get overloaded)
- Rebalancing is expensive

Use case:
- SQL DB
- Time-based Logs
- OLAP systems

### Hash-based partitioning ###
How it works:
1. Apply a hash function to the key
2. Assign to shard based on hash value
```txt
shard = hash(key) % N
```
Pros:
- Even distribution of keys
- Avoids hotspots
- Simple and fast

Cons:
- No ordering
- Range queries require hitting all shards
- Rebalancing is painful with naive hashing

Use case:
- KV stores
- Caches
- High-write systems

The problem with naive hashing:  
When the number of shards changes:  
```text
old: shard = hash(key) % 5
New: shard = hash(key) % 6
```
Almost every key moves to a different shard.  

Consistent hashing minimized key movement when nodes are added or removed.

Instead of:
```text
hash(key) % N
```
It uses
- A hash ring
- Keys and nodes both hashed into the same space
- Keys map to the next node clockwise

When adding/removing a node:  
Only keys assigned to that node clockwise moved. 

Use virtual nodes to further improve balance.
